## Context

The newsflash SPA stores article hide/readlist state in localStorage using article IDs generated by `hashString(link)` in `base-parser.ts`. The current `hashString` is a DJB2-style 32-bit hash that produces plain numeric strings (base-36 encoded). The `removeHiddenBySource` function in `use-article-state.ts` expects IDs to contain a `sourceId:` prefix, but no such prefix exists in the generated IDs. This mismatch means source-based removal is completely broken.

Additionally, lookups (`isHidden`, `isInReadList`) use linear array scans, and the 32-bit hash space creates non-trivial collision risk at scale.

## Goals / Non-Goals

**Goals:**

- Make `removeHiddenBySource` functional by ensuring article IDs contain the source prefix
- Reduce hash collision probability to negligible levels for the expected article volume (tens of thousands)
- Achieve O(1) article state lookups during render
- Handle migration from legacy ID format gracefully

**Non-Goals:**

- Cryptographic hash strength (we need fast, low-collision hashing, not security)
- Backward compatibility with legacy localStorage data (clearing is acceptable)
- Changing the localStorage key names or storage structure beyond ID format

## Decisions

### Decision 1: Article ID format `${sourceId}:${hash}`

Concatenate the source identifier and hash with a colon separator. This makes `removeHiddenBySource` work via `startsWith` matching and improves debuggability.

**Alternative considered**: Store source as a separate field in hidden IDs (changing from `string[]` to `{id, source}[]`). Rejected because it changes the storage schema more than necessary and the prefix approach is simpler and already matches the existing `startsWith` filter code.

### Decision 2: 53-bit hash function

Replace the 32-bit DJB2 hash with a 53-bit hash that uses two independent hash passes combined into a single value within JavaScript's safe integer range (`Number.MAX_SAFE_INTEGER`). This reduces birthday-problem collision probability from ~1 in 65K (at 10K articles) to ~1 in 9 billion.

**Alternative considered**: `crypto.subtle.digest('SHA-256', ...)`. Rejected because it is asynchronous, which would complicate the synchronous parsing pipeline. The 53-bit hash provides sufficient collision resistance for this use case.

### Decision 3: Set-based lookups with useMemo

Create `Set<string>` instances via `useMemo` derived from `hiddenIds` and `storedReadList`. The `isHidden` and `isInReadList` callbacks use `Set.has()` for O(1) lookups.

**Alternative considered**: Keep arrays and optimize only if profiling shows issues. Rejected because the fix is trivial, the improvement is guaranteed, and the current O(n) scan runs on every article card render.

### Decision 4: Clear legacy data on migration

On first load, detect IDs that lack a colon separator and discard them. This is acceptable because hidden/readlist state is ephemeral user preference data, not critical application state.

**Alternative considered**: Re-hash all articles on load and attempt to match legacy IDs. Rejected because we do not have article links available at migration time (they come from feed fetches), making re-hashing impossible.

## Risks / Trade-offs

- **[Users lose hidden/readlist state on upgrade]** -> Acceptable: this is non-critical ephemeral data. Users may see previously hidden articles once, which is a minor inconvenience.
- **[53-bit hash still not collision-free]** -> At 10K articles the probability is ~1 in 9 billion per pair, which is negligible. True collision-free would require storing full URLs, increasing storage size significantly.
- **[Source ID must be stable]** -> If source IDs change (e.g., feed URL changes), `removeHiddenBySource` will not match old entries. This is the existing behavior and is acceptable.
